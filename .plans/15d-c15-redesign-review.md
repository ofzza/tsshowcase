# C15 redesign amendment: choices and review (plan 9)

Plan 9 of the representation redesign's application (`08b-representation-redesign.md` §12, `08e` E7): the redesign amendment of `chunk-15-vite-helper.md`. Checklist sources: 08b §7.9, §7.10, §12 (C15); `08e` E2; `02b-c2-b9-review.md` "Saved for the later plans" (C15); `05b` Fix 28; `07b` QC; `01e` (runtime tests, the extra Vitest project); C2 "Recorded for later chunks" (C15, B9); C5 §8 and its recorded points; C7's recorded points.

## Choices made by the draft (settled with the user one by one, 2026-10-21)

- **K1 (1/8, ok, option a; D210):** rendered docs reach the site as one lazy chunk per doc in builds (`virtual:tsshowcase/docs`, `\0tsshowcase-doc:<id>`, rendered before the Vite build through `ctx.docs.render`), and in `dev` are rendered on request from the current snapshot (`/@tsshowcase/docs/<id>.json`, `no-store`, the revision in the URL); the runtime's `loadDoc(id)` covers both. Rejected: docs inside the embedded data via an async `prepareData` (everything in the main bundle, everything re-rendered per snapshot); fetched JSON files in builds (an extra fetch path and naming scheme).
- **K2 (2/8, ok, option a; D210):** `ViteApp.selectDocs?(representation) => DocRef[]`, default every `DocRef`; only selected docs are rendered and embedded; unknown refs are an error naming the doc; `-base-react` narrows it (C10). Rejected: default none (silently doc-less sites), no hook (gives up L20 for docs).
- **K3 (3/8, ok, option a):** `prepareData` returns `PreparedData`, a JSON object keeping `revision` and `tests` (replacing the hierarchy-shape contract of S12/T10); `applyTestUpdate` merges into `tests` by C2 §4.4's table and sets `revision` to the update's; pure, shared by the browser and the dev server (an import-free file). Rejected: revision tracked outside the data; documenting slimmed `tests`.
- **K4 (4/8, ok, option a):** one "last applied" revision in the runtime across both streams; one `hello { revision }` on the first subscription (either stream) and after a reconnect, answered to that client alone with one `tsshowcase:data` message carrying the current snapshot (test updates included); `onTestUpdate`-only apps don't see it, so apps rendering test results also subscribe to `onData` (documented). Rejected: a synthesised full `TestsUpdate` reply; per-stream hellos (only meaningful with two producers). *(Refined by the review: no reconnect hello, Fix 8; delivery rules, Fix 7.)*
- **K5 (5/8, ok, option a):** showcase loaders for every distinct showcase file on any node, at any association level; no selection hook. The user leaned towards a `selectShowcases` hook for symmetry with `selectDocs`, and chose (a) because a hook could hide a broken showcase from the build; one can be added later, additively.
- **K6 (6/8, ok):** the dogfood layout: `pipeline/` area (`buildSite.ts`, `startDevServer.ts` with tests, type-only `ViteApp.ts`), runtime areas `data/`, `live/`, `docs/`, `showcases/`, `stylesheets/`, `theme/`, `document/` (one file per concept, a README each), `runtime/internal/` without public symbols, and `client.d.ts` in its own `src/client/` area (fits whichever way C8 decides about ambient declarations).
- **K7 (7/8, ok, option a):** only `runtime/internal/virtual.ts` imports the virtual ids; the `unit:tsshowcase-base-vite:runtime` project (jsdom) aliases them to stubs in `test/virtual/` (outside the `src` scope); tests use `vi.mock`/`vi.doMock`; no `exempt`. Rejected: input injection (the wrappers need tests anyway), an `exempt` relying on C12. *(Refined by the review, Fix 4: tests mock the adapter, which also owns `import.meta.hot`; the aliases remain for the adapter's own test.)*
- **K8 (8/8, ok, option a):** the dev server's store ignores a data or test update whose revision isn't higher than its own, with a debug log, like the runtime. Rejected: applying it anyway (silent regression), a loud warning (noise; C11's tests catch ordering bugs).

## Review

Two zero-context reviewers, read-only (with the no-sudo/no-system-changes rule): **R1 fidelity and completeness** (C15 vs 08b §7.9/§7.10/§12, E2, D160–D210, C2 §4/§4.4/§5.8/§6/§8 and every C15 checklist source) and **R2 fit and implementer's read** (C15 vs C1 §4/§8, C5 §4.6/§8, C7 and C2's process-state rule, C3, the super-plan and the AGENTS rows; Vite 8.3.4 / Rolldown 1.2.14 checked by an actual build and a tsc 6 check in a scratch directory). R1: 13 findings, R2: 17. Verified to hold: one chunk per dynamically imported virtual doc module, with path-free names; per-client replies through `server.ws.on(event, (data, client) => …)`; host and CORS checks before `configureServer` middlewares, no SPA fallback with `appType: 'custom'`; a hello sent before the socket opens waits for the connection.

### Questions (settled one by one with the user, 2026-10-21)

- **QA (1/5, ok, option a; R1 F1):** `selectDocs` and `prepareData` take `(representation, state)`; the store keeps `state` per snapshot (`ctx.state`, then each `DataUpdate.state`).
- **QB (2/5, ok, option a‴; R1 F10, R2 G11):** the output path check is a backstop against the toolchain, a module or the CLI leaking this machine's layout, not a judgement of user content. The user asked for its purpose, objected that legitimate paths in READMEs (`/etc/`, `/usr/bin/`) would trip a detector, and proposed excusing any occurrence found in the original doc source (adopted). The user then rejected searching the machine for "concrete strings" (home directory, install directories): it digs where it shouldn't, varies by machine, and costs; and asked why not detect paths generically: Claude explained that bundled user and dependency code is full of path-like strings (`/api/users`, `/dev/null`) that no doc source excuses. Settled: candidates come **only from paths the build itself handled** (`repoRoot` and its real path, `cacheDir`, the directories of the entry, preludes, theme stylesheets, showcase files, showcase Vite config and Rolldown's absolute module ids, plus cwd-relative forms); an occurrence is **excused** when the same string appears in the raw source of a doc rendered in this build (the user's proposal); everything else fails, naming the file and string. C11 uses the same rule. Rejected: (d) dropping the check.
- **QC (3/5, ok, option a; R2 G10):** one chunk per doc and per showcase is a default, not a protected key; a showcase Vite config may turn code splitting off; tests use the default config; documented.
- **QD (4/5, ok, option a; R1 F7, R2 G8):** dev doc answers are `{ revision, doc }`; `loadDoc` rejects with `StaleDocError` for an answer older than the last applied revision; no query parameter. The user asked whether dropping the parameter risks browser caching: no, `Cache-Control: no-store` on the response and `cache: 'no-store'` on the request each prevent it; (a+) keeping `?v=` as a documented cache-buster was offered and not chosen. Doc ids can change between snapshots (D184), documented.
- **QE (5/5, ok, option a; R2 G15):** confirmed K5's consequence: every showcase file is compiled, so a broken weak one fails `build`; documented in C13.

### Fixes (applied)

- **Fix 1 (R1 F2, R2 G1):** `PreparedData` is an interface `{ revision; tests }` (a `JsonObject` intersection rejects interfaces, verified with tsc); JSON-safety stated in prose; a type test that `Representation` is assignable.
- **Fix 2 (R1 F3, R2 G3):** `PreparedData` and `EmbeddedDoc` declared on the runtime side (`runtime/data/`, `runtime/docs/`), exported from both entries, imported by `ViteApp.ts`.
- **Fix 3 (R1 F13, R2 G3):** two TS projects: the runtime build project (`dom`) and the Node project referencing it; the runtime project compiles `applyTestUpdate` and `selectTheme` once; tests crossing both halves live in the Node Vitest project.
- **Fix 4 (R2 G2):** every `import.meta.hot` call and every virtual-id import lives in `runtime/internal/virtual.ts`, which offers callback registration; runtime tests mock the adapter; the runtime tsconfig includes `vite/client` types.
- **Fix 5 (R2 G4):** `client.d.ts` is copied to `dist/client/` by the sidecar copy step (C1 A1); `./client` conditions `source` and `types`.
- **Fix 6 (R2 G5):** `virtual:tsshowcase/data` exports `mode: 'build' | 'dev'`, generated by our plugin.
- **Fix 7 (R1 F5, R2 G6):** messages before the first listener are ignored; the counter advances only on delivery to a listener of the message's stream; the hello goes out in a microtask after the first subscription; apps subscribe to both streams in the same tick; tests for both orders.
- **Fix 8 (R2 G7):** no reconnect hello (Vite's client reloads the page after a lost connection).
- **Fix 9 (R1 F6):** one definition of showcase files (by `ShowcaseAssociation`; a test-and-showcase file counts as a test) used by `optimizeDeps.entries`, the loaders and the dev reload rule.
- **Fix 10 (R1 F8, R2 G13):** the store starts from `ctx.representation`, `ctx.docs`, `ctx.state`.
- **Fix 11 (R2 G9):** a throwing `selectDocs`/`prepareData` (or an unknown ref) in `dev` is logged and keeps the previous snapshot and revision; the hello and data-module paths log and send nothing.
- **Fix 12 (R2 G12):** on an abort `buildSite` rejects with `ctx.signal.reason` once the current render or build settles.
- **Fix 13 (R1 F4):** a test named after every runtime exporting file, listed with its cases.
- **Fix 14 (R2 G10 note, G13):** `EmbeddedDoc` without `format`/`assets`; `applyTestUpdate` in `data/`; "import-free" allows type-only imports; docs render one at a time; the runtime project's globs follow C1 §4; doc import specifiers use the public id `virtual:tsshowcase/doc/<id>`.
- **Fix 15 (R1 F9):** internal tests cite C1 §4/§10 and D56, not D10.
- **Fix 16 (R1 F11, R2 G14):** AGENTS open points: C8 (G17), C10, C11, C12, C13 rows gain the plan-9 hand-offs.
