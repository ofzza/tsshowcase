## Choices made by the draft (settled with the user one by one)

- **Q1 (1/9, ok, option a) → D211:** `export * as ns` makes every member public as `ns.<member>`; each member attaches to its own declaring file as with `export *`; the namespace name is no symbol. Rejected: (b) one `constant` symbol on the barrel (the functions behind it would escape tests); (c) both (duplicates, a doc forced on a barrel). Namespace declarations (`export namespace X`) stay ordinary symbols.
- **Q2 (2/9, ok, option a) → D212:** ambient module declarations (`declare module '…'`) and global augmentations are never symbols; a non-module entry (e.g. `-base-vite`'s types-only `./client` → `src/client/client.d.ts`) yields nothing, no issue (debug log). C1 §8 wording: "entry files only re-export" applies to module entries. Rejected: (b) a `type` symbol per ambient module (invented identities); (c) a warning (noise for a deliberate pattern; fails this repo's `strict: warnings`).
- **Q3 (3/9, ok, as drafted) → D213:** (a) a hook is callable and named `use` + upper-case letter or digit; V5's "returning something" read as callable (`void` hooks are common); (b) an anonymous default export uses its declaring file's base for the name tests (identity stays `default`); (c) values typed `any` are classified by initializer syntax (function/arrow → `function`, class expression → `class`, else `constant`; an untyped `memoize(g)` is a `constant`, documented, fixed by `kinds`); (d) `react/approximate-kinds` is a package warning issue raised only when the syntactic fallback classified a component there. Rejected: non-`void` hooks only; anonymous defaults never components; call expressions as functions; a logged warning, or a warning whenever `@types/react` is missing.
- **Q4 (4/9, ok, option a) → D214:** showcasing components are the default export and every upper-case named value export that isn't syntactically a literal, object, array or template (U19); per-component `title` (string literal) and `shell` (literal `true`) are static property assignments (`Sizes.title = '…'`) read syntactically, so the file exports only components and stays a Fast Refresh boundary (C15 S5, 08a U20); C10 derives titles when unset. Rejected: (b) a per-file settings object keyed by export names; (c) React's `displayName` (mixes DevTools naming); (d) D149's per-file exports. C10 finalises the format (D96).
- **Q5 (5/9, ok, as drafted) → D215:** `init <path>`: an existing in-scope directory (stubs for every direct/collection node below), an existing exporting file (its node), a nonexistent path with a source extension (a new file item), any other nonexistent path (a new directory with `<Name>.<ext>`), anything else a clear error; the docs stub is the directory `README.md` (else `<base>.md`); the re-export goes to the module entry whose source directory is the nearest ancestor (else `'.'`), no entry → error (U8, U18); `headless` writes the four files and suggests a collection (no directory configs written). C6's registry and C9: the positional is `<path>` (wording).
- **Q6 (6/9, ok, option a) → D216, C2 amendment B11:** `RepresentedItem.requires: readonly ('docs' | 'tests' | 'showcase')[]`, the required resource types after kind overrides, module kinds and exemptions, set by the CLI wherever items appear; `scaffold` and C10's presentation use it, no module re-implements the kind table. Rejected: (b) also `exempt` (later, if C10 wants it); (c) exporting the table and exemptions; (d) running the check in `init` (reverses 02b Q3).
- **Q7 (7/9, ok, option a):** C8's analysis issues carry `package` and name the file in the message, no `path`: their files (manifest, tsconfigs, entries, ignored files) are often out of scope, and C2 §9 doesn't place an out-of-scope `path`. Rejected for now: (b) a C9 rule placing out-of-scope paths on the package root (a later additive refinement); (c) `path` only when in scope.
- **Q8 (8/9, ok, option a):** `-test` gains `createTestRepoInput`, `createTestTree` and builders for `Representation`/`FileInput`; C9's end-to-end tests over C8's fixtures are the safety net. Rejected: (b) the real CLI pipeline through an internal subpath (a workspace cycle; C8 is implemented before C9); (c) inline contexts everywhere.
- **Q9 (9/9, ok, option a):** `-base-react` declares every base option now (incl. `viteConfig`, `showcaseStylesheets`, `showcaseSetup`, implemented in C10); `homeDocs` and how a layout module extends the schema come with C10. Rejected: (b) designing schema extension in C8; (c) declaring nothing C10 implements.

### Questions (for the user, one by one)

- **QA (1/6, option b, the user's choice: "I like the explicitness of (b). I don't mind the dependency"; revises Q4 → D214)** (R1#1, R2#4): the static-property settings (`X.title = …`) type-check only on function declarations and unannotated `const` functions; `memo`/`forwardRef` results, class components and annotated consts give TS2339 (verified); an anonymous default export has no name to assign to. Revisits Q4. **Outcome:** a showcasing component is an export whose value is a call to the helper `showcase(component, settings?)` (QA-1 (i): only wrapped exports count; a `*.showcase.{tsx,jsx}` file without one gets `react/showcase-empty`; the U19 heuristics are dropped); the helper lives in a browser-safe subpath `@ofzza/tsshowcase-base-react/showcase` (with `ShowcaseProps`), returns the component unchanged (copies may differ; exports stay components for Fast Refresh), and C8 reads its settings syntactically: the binding imported from that subpath (aliases allowed), an object literal with a string-literal `title` and/or `shell: true`, else `react/showcase-meta` (QA-2); the user's package (or the root, hoisted) declares `@ofzza/tsshowcase-base-react` as a devDependency, else the `verify` warning `react/showcase-dependency`; `scaffold` writes the import and notes a missing dependency, never edits `package.json` (QA-3). Rejected: (a) static properties widened (forms needing wrappers), (c) JSDoc tags (configuration in comments, D158), (d) a per-file settings export.
- **QB (2/6, ok, option a; → D215)** (R1#7, R2#5): `init` targets: only in-scope directories qualify as written (a package directory under `scope: ['src']` is an out-of-scope connector; `.` in a workspace is outside every package); nonexistent targets can't be classified through the contract (`exists` is false for ignored and missing alike; scope matching would duplicate C4). Who resolves and validates the target. **Outcome:** C9 turns the positional into a `RepoPath`, rejects ignored targets and those outside the repo, and for nonexistent ones those outside every package or out of scope (C4's `inScope`/`packageOf`); C2 §5.10 (with B11): `ScaffoldContext.target: ScaffoldTarget { path: RepoPath; type: 'directory' | 'file' | 'new'; package?: RepoPath }` (`package` unset only for an existing directory above every package, e.g. `.` in a workspace); the module acts on the in-scope nodes at or below an existing directory (package directories and `.` included) and errors only when there are none. Rejected: (b) the module matches `scope` itself; (c) existing in-scope targets only.
- **QC (3/6, ok, option a; → D216)** (R2#6): B11 doesn't cover new items (no `RepresentedItem` yet), so `scaffold` would apply the kind table itself and couldn't honour an `exempt` matching the new path; B11's union is closed and unordered. **Outcome:** `-api` exports `WELL_KNOWN_KINDS: { [kind]: KindDescriptor }` (the D162 table; one place for the CLI's check, modules and docs; part of B11); new items get every stub their kind requires (well-known or the module's `kinds`), exemptions are not applied to them (documented: `init` never overwrites, delete an unwanted stub); `requires` is an open union in a fixed order (docs, tests, showcase). Rejected: (b) CLI-computed exemptions for a new target (partial: `#name` keys can't match yet); (c) the table hard-coded in the module.
- **QD (4/6, ok, option a; → D215)** (R1#5, R2#7): the docs stub: D196/08b §10 say stubs by name for files and `README.md` for directory targets; a placeholder README vouches for every sibling (D174); a README at a package or repo root is a home doc and doesn't count (E1). Revisits Q5's docs stub. **Outcome:** by target type: file targets (existing or new) get `<base>.md`; directory targets (existing or new) get `README.md` in each directory below with exporting files lacking docs and no README; in a package or repo root directory always `<base>.md` (a root README is a home doc). Rejected: (b) always `<base>.md`; (c) README everywhere except roots (silent vouching for siblings on file targets).
- **QE (5/6, ok, option a)** (R1#8, R1#9, R2#3): tsconfig selection: solution-style tsconfigs (`files: []` + `references`, the Vite React template), per-part tsconfigs (a runtime directory with `dom`/`jsx`, C1 §4, C15 §1), the AGENTS open point's actual meaning; ambient `.d.ts` files from `fileNames` (`vite-env.d.ts`, `declare module '*.svg'`) dropped from the program; `react/showcase-in-build` with a solution-style build tsconfig. **Outcome:** per entry source, the `tsconfig` option, else the first `tsconfig.json` from the source's directory up to the package directory, then the repo root, whose parsed `fileNames` include the source; solution-style configs followed through `references` recursively; defaults when none; one program per distinct effective config; the chosen config's `.d.ts` `fileNames` inside the package (outside `node_modules`) added as root files for context, never as exporting candidates; a symbol reached from entries in different programs is classified in the first entry's program; §4.5 and the dist → source mapping follow `references` too; fixtures for a part tsconfig and a solution-style one. Rejected: (b) one tsconfig per package, part configs a C10 risk (would misclassify `-base-react`'s runtime components).
- **QF (6/6, ok, option a)** (R2#2): subpath patterns: `-theme-default`'s `"./css/*": "./css/*"` has no extension to classify; a warning would fail this repo's dogfood check; C1 §8's "every subpath carries `source`" doesn't hold for `./css/*`, `./package.json` or JSON subpaths. **Outcome:** patterns are expanded against existing files: the target in condition order, mapped through the dist → source rules applied to the pattern's prefix and suffix when it points into an output directory, the `*` expanded over existing files (ignored = nonexistent); every script or declaration module matched is an entry, non-script matches are skipped silently; `react/entry-pattern` removed. C1 §8 wording: the `source` condition is required on subpaths resolving to scripts or declarations only. Rejected: (b) classify by extension and warn on script patterns.
