## A. Record as open points or duty assignments (no change to an approved plan)

| #   | Finding | Proposed record |
| --- | ------- | --------------- |
| L2  | **Test errors leak absolute paths.** `TestError.message`/`stack` (and `unhandledErrors`) contain the build machine's paths (`/home/…/x.test.ts:10:5`). They go into `ShowcaseData` and the bundle, against inclusion rule 2. C11's own "no absolute build-machine paths" check would then fail `build` whenever a test fails, against D8. | **C11:** while assembling the data, rewrite `repoRoot` (plain and `file://` forms) in every `TestError` string to repo-relative paths. C2 principle 3 gets one clarifying sentence (free text is relativised by the CLI). C7 only guarantees the `file` fields. |
| L4  | **What is the repo root?** No plan says how the root is found: `--cwd`, the process cwd, the git top level, or the nearest config file. Nor does any plan say what happens when the CLI runs inside a workspace package, or what the positional `build [outDir]` is relative to when `--cwd` is given. | **C4/C6 open point.** Recommendation: the root is `--cwd`, else the process cwd, with no upward search. Positional paths are relative to the process cwd, like any shell argument. Inside a workspace package, a package-level config (one with `skip`) found at the root is an error that says "run from the workspace root". |
| L6  | **The React showcase file interface is needed by C8, before C10.** C8 scaffolds showcase stubs and verifies "a showcase default-exports a component", but its plan and implementation come before C10, where the `colorScheme` prop and the `shell` opt-in are specified. D61 (several showcases per unit) also has no React file convention yet: several `*.showcase.tsx` files, or several named exports in one file? Either way, how `ShowcaseEntry.name` is derived is open. | **C8 open point:** settle the file naming, the default-export signature (`{ colorScheme }`), `export const shell`, and how several showcases per unit and their names are expressed. C10 implements against that. |
| L7  | **Where React and Vitest resolve from in workspaces.** With pnpm, or when only `packages/ui` depends on React, resolving from the repo root finds nothing. D91 would then bundle a second React while the user's showcases import their own, which is the duplicate-React pitfall. Two packages on different React majors can't share one app at all. | **C10 open point (refines D91):** resolve React from the package that owns each showcase. Every showcased package must resolve to the same React, or the CLI raises a clear error. Use the fallback only when no showcased package has React. **C7:** the same question for `vitest/node` (joins the existing "root or per package" point). |
| L9  | **Catalogue gaps that D92 turns into blockers.** Outside `.tss-content` a theme can only style catalogue classes. Under pnpm, or when the user only installed the CLI, that import fails, or it resolves to a different `-api` version than the CLI's. | **C6 open point:** jiti aliases `@ofzza/tsshowcase-api` to the CLI's own copy for path-loaded plugins, and this is documented (C13). Plugins installed as packages keep their own dependency. |
| L13 | **Yarn PnP** repos have no `node_modules`, so `createRequire(repoRoot)` (Vitest, React, TypeScript) fails in confusing ways. | **C4 open point:** detect `.pnp.cjs` and fail with "Yarn PnP isn't supported in v1; use `nodeLinker: node-modules`". |

## B. Needs a decision (recommendation given)

| #   | Finding | Recommendation |
| --- | ------- | -------------- |
| L1  | **README images and other local assets.** `![](./docs/screenshot.png)` in a README falls under D73's "anything else → the VCS host". That gives a `blob` URL, which is an HTML page, not the image. It breaks for private repos and is a third-party request (rule 2). No plan bundles README assets. stdblox-style READMEs with screenshots would break. | **C2 contract addition:** `Doc.assets: { source: RepoPath; path: string }[]`. C5 rewrites local `img`/`source`/`video` URLs to site-relative `path`s (e.g. `assets/docs/<hash>.<ext>`). The module emits the files in `build` and serves them in `dev` (`-base-vite` does both). The CLI checks that every listed asset is in `BuildResult.files`. |
| L3  | **`unhandledErrors` and `unmapped` tests never reach the reader.** The spike showed a TS syntax error makes type tests pass silently and surfaces only in `unhandledErrors`. But `TestResults` has no slot for them, `ShowcaseData` has none either, and `--fail-on-test-failure` ignores them. `TestResults.unmapped` ("for diagnostics") goes nowhere either. | **C2 contract addition:** `TestResults.unhandledErrors?` and `ShowcaseData.tests?: { unhandledErrors; unmapped: RepoPath[] }`. The CLI prints them, modules show them on the home page, and strict mode fails on unhandled errors. |
| L5  | **The always-ignored output directory.** C4 always ignores the configured output directory, so by default `./showcase`. In stdblox that is the user's **source** directory, which `check` would then silently drop from the report. Conversely, a site built to a non-default positional `build docs/site` isn't ignored by a later `check`. | Ignore **any directory containing tsshowcase's output marker file** (C11 writes it), plus an explicitly configured `outDir`, but not the implicit default. |
| L8  | **Responsive breakpoints vs the styling rule.** Custom properties can't be used in `@media`/`@container` conditions, so any responsive shell needs literal breakpoints. Those pass `design-values`, which checks declarations only, but they break the requirement ("no styling unless exposed as a variable or class, or inferred from one"), and a theme can't change them. | **The module switches layout by attribute:** it reads a catalogue variable `--tss-layout-breakpoint` (computed style, `ResizeObserver` on the host) and sets `data-layout="narrow"\|"wide"` on `.tss-shell`. CSS uses `[data-layout=…]` (a `tssData` value), so the breakpoint stays a themeable variable. Lint rejects length literals in media/container queries of module and theme CSS. A C3 amendment, planned with C10. (The alternative, fixed breakpoint constants, isn't themeable.) |
| L10 | **Shell-mode showcases with their own scheme.** C3 §1 says the scheme selector "sets the configured theme matching the selected scheme on its stage". But the scoping wrapper only matches `.tss-shell[data-theme]`. Putting `tss-shell` on the stage drags in the shell's own layout CSS, and two nested theme scopes resolve equal-specificity class rules by stylesheet order, not proximity. | **Simplify:** shell-mode showcases (D41's dogfood only) follow the shell's theme and get no scheme selector. C3 §1 and C2 rule 7 get one sentence each. |
| L11 | **`BuildContext.themes` includes `reference`**, which may be a filesystem path (D9). A module naturally embeds the theme list for the switcher, which would leak that path (rule 2). | Narrow it to `Pick<ThemeDefinition, 'name' \| 'label' \| 'scheme'>` (C2 §5.8 type edit). |
| L16 | **Process: run the "v1 cut line" review (K21) now, not after all plans.** P3 is about to spend planning detail on features the cut line might drop or defer: per-package config files and `optionFlags` (C6), the published `-lint` package, the compat guards, the full scoping transform's topological merge. | Hold a short cut-line pass **before** planning C4–C15, then plan P3 against the reduced scope. Keep the post-planning review as a final check. |
| L17 | **C10 is the largest chunk by far:** the React wrapper, the React fallback, `runTests` mapping, all runtime building blocks, the isolation duties, the default layout and the dogfood showcases. | Split it into **C10a** (`-base-react` runtime: Vite wrapper, React resolution, `runTests`, host/isolation, building blocks) and **C10b** (`react-default` layout and the dogfood showcases), each with its own plan. Optional. |
