## VCS ref (D205, from the user's question during O8, 2026-10-21)

The user asked why VCS links use `HEAD` (drift) rather than the exact commit the showcase was built from. Claude's analysis: pinning removes drift for a clean, pushed checkout (CI), but D110 avoided git entirely, a local commit may be unpushed (404s) and the working copy may be dirty (D129); proposed (a) `vcs.ref` defaulting to `HEAD`, auto-filled from CI variables, (b) reading `.git`, (c) the status quo. **The user's design (recorded as D205):** `vcs.ref` / `--vcs-ref`: `HEAD`, `CURRENT` (default; the commit read from `.git` without running git) or any other value as a commit, tag or branch; the keywords case-insensitive (occluding same-named refs, accepted); unpushed commits and uncommitted changes accepted as caveats; `.git` must be a directory, easily readable, at the scanned root or above (a second upward-search exception, like C4 §3's); otherwise an error demanding an explicit `vcs.ref`, **no fallback** to `HEAD`; no CI variables. Claude's additions, within that design (all four **approved by the user**): the reader reads only `HEAD`, loose refs and `packed-refs`, never `config` (M21); the error is raised only when VCS links are needed; `VcsInfo.ref`; an optional `{ref}` placeholder in user templates; `build` logs the ref. Applied as a backtrack to C4 §3, §9, §10, §12 and its C6 recorded point (noted in C4's status line), C2 §4 `VcsInfo` and §10 config (wording note), C5 §9 tests, AGENTS (D205, D110's status, the C11 and C13 open points); C6's key and flag in plan 7.

## Choices the draft made beyond the decisions (discussed one by one)

- **O1 (ok, option a):** prefixed ids per element: headings `<doc-id>--<slug>`; footnotes `<doc-id>--fn-<label>`, `--fnref-<label>`, `--footnote-label` (the sanitiser's `user-content-` removed first, as D127); author anchors `<doc-id>--user-content-<x>` (kept, so they never collide with a heading slug); fragment lookup: heading slug, then author anchor (`#x` or `#user-content-x`), then footnote id; a heading wins over an author anchor (D128). Rejected: (b) dropping `user-content-` from author anchors (duplicate ids with a same-named heading); (c) keeping it on footnotes (longer ids; the rare `## Fn note` collision is D127's accepted edge case).
- **O2 (ok, option a):** when `resolveRoute` returns `undefined` for a doc's link-selection node, its headings keep their ids but get no permalink (a permalink that leaves the showcase is surprising and shows the default branch; matches the old handling of docs without a page). Rejected: (b) a permalink to the VCS host (leaves the site; a dead `unlinked` icon without VCS info); (c) a permalink to wherever the module shows the doc (C5 can't know; the module's presentation).
- **O3 (ok, option a):** `createDocs({ representation, scan, resolveRoute })` → `{ access, assetsOf, renderedAssets }`, one per snapshot; `checkDocs({ representation, scan })` → `{ issues, unlinkedVcsLinks }`; rendering parses only the doc and the targets its anchors point into, target id sets cached per doc for the snapshot; parsing and resolution shared with `checkDocs` (D124). Rejected: (b) a whole-set pre-pass (parses every doc even when few are shown); (c) bookkeeping on `DocsAccess` (exposes CLI internals to modules; C2 keeps it to `render`/`read`).
- **O4 (ok, option a):** `checkDocs` counts unlinked VCS links over every `DocRef` (`unlinkedVcsLinks`); `build` runs the check first (D164), so C11 prints the one-time `no-vcs` warning (D110) from that count, deterministic and independent of what the module renders. Rejected: (b) from rendered docs only (depends on the module, arrives late); (c) both (more wiring for a one-line warning).
- **O5 (ok, option a):** `assetsOf(ref)` runs the shared pipeline up to media resolution (parse, resolve, safety checks, hashing), no HTML and no `resolveRoute` calls, cached per path; C11 calls it for every `DocRef` to fill `docAssetsDir` before each `onDataUpdate`; `render` reuses the cached result, so paths agree. Rejected: (b) rendering every doc in `dev` (HTML and module calls for docs never shown); (c) assets from `checkDocs` (`check` deliberately doesn't hash, and runs outside `dev`).
- **O6 (ok, option a):** C5 works per doc path: `checkDocs` checks each path once (C9 attaches each issue to every node holding the doc, D180); `render` caches per path (the HTML depends on the doc's location and the representation, not on the referring node); a module may show a doc on several pages, never twice on one (C2 rule 6). Rejected: (b) per `DocRef` (duplicate issues, repeated renders); (c) node-dependent HTML (needs the module's presentation).
- **O7 (option b′, the user's choice; recorded as D204):** fragments on node targets without `doc` (e.g. `Button.tsx#L10`) are passed to the module as written in a new `RouteTarget.fragment` (additive C2 §5.6 change), never validated or reported; the module returns its page URL or `undefined` (→ the VCS host with the fragment kept); `-base-react` defaults line anchors to the VCS host when VCS info is known (C10). The user: no downside to passing the fragment; worst case it doesn't work, and it lets a module route to VCS or implement "route to line number" itself. Discussion: Claude first recommended (a) dropping silently, then (a′) a CLI rule sending line anchors to the VCS host; the user asked whether VCS-vs-showcase is the module's decision (it is per node through `resolveRoute`, but the module couldn't see the fragment). Rejected: (a), (a′), an info note (no such severity), a `docs/broken-anchor` warning (flags correct GitHub links). Applied to C2 §5.6 (wording note in its status line), D183's text, D204, C5 §4.1, §4.2, §9, recorded C10 point.
