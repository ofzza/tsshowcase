## Choices made by the draft (settled one by one, all ok)

- **CC1 (1/10, ok, option a):** directory configs (§4.1): `loadDirectoryConfigs(scan, resolved)` after the scan; several files in a directory → none loaded, one `config/several-configs` (error) with the directory as `path`; JSONC forms parsed like the config (empty `.tsshowcase` = `{}`), JS/TS forms via jiti with D117's aliases, default export an object or `true`, a function rejected (as D115); schema violations a thrown `ConfigError`; kind values checked; result per directory with its base, **no merging** (C9 merges, J8). Rejected: (b) load all of several files and let C9 decide (runs code that won't apply, splits the rule); (c) C6 also merges (most `config/*` issues need the analysis, J8).
- **CC2 (2/10, ok, option a):** runner failures (§11): a **pinned** runner (`testRunner`) failing to resolve, load, version-check or shape-check → thrown `PluginError`; an unpinned candidate failing to load, or whose `detect` throws → `tests/runner-failed` (error), the others still used. Rejected: (b) always throw (one broken optional candidate stops every action); (c) always an issue (a pinned run continues with no runner, surfacing only via `tests/no-runner`).
- **CC3 (3/10, ok, option a):** when runners load (§2, §11): on demand after the scan, `resolved.loadTestRunners(repo)` → `{ runners, issues }`, once per invocation, by every action (`check` and `init` list, `build`/`dev` list and run); in `dev` fixed for the session (C11); like `loadThemes()`. Rejected: (b) eager loading in `resolveConfig` (splits loading from detection); (c) C9/C11 assemble candidates (candidate rules in two chunks).
- **CC4 (4/10, ok, option a):** what C6 merges (§2, §7): only `moduleOptions` (D69, D148); `rules` stay per source (D176); `directories`, `kinds`, `exempt` handed to C9 per source as written, with the source's base directory (`configMaps`), the same form as `loadDirectoryConfigs` (CC1); keys as written keep globs and the text issues quote. Rejected: (b) keys rewritten repo-relative (glob escaping, original text lost); (c) C6 pre-merges root and package maps (splits D188's chain and `config/shadowed`).
- **CC5 (5/10, ok, option a):** module kind keys must match `^[a-z][a-z0-9-]*$` (§9.1; `03c`), else a load-time `PluginError`; safe unquoted in `data-kind` selectors, no case-folding; C2 §5.1 worded to match. Rejected: (b) upper case and `_` allowed (kinds differing only in case); (c) no constraint, escaping everywhere.
- **CC6 (6/10, ok, option a):** module `testRunners` resolution (§11): built-in names as built-ins; npm names from the module's own location only; relative `file:` against the module file (C2 §5.1 as written; no fallback to the repo or the CLI: a module naming a runner must depend on it); failures per CC2 (`tests/runner-failed` naming the module and reference). Rejected: (b) fall back to the repo root, then the CLI (hides the packaging bug, may pick another version).
- **CC7 (7/10, ok, option a′):** the hints are runtime `ConfigError` hints. The user asked what they were for; Claude's revision: nothing is published (`0.x`, D80), so migration hints for never-shipped names help nobody and leave dead names in code and tests. Kept: fixed hints for mistakes a new user could plausibly make only: `exclude` in a package config → `skip` (D69), `build <dir>` → `--out <dir>`, `build --strict tests` → `--strict=tests` (D167), top-level `collections` → "directory configs only". Dropped: `check`, `failOnTestFailure`, `units`, `moduleOptions.testRunner` (incl. C8's planned hint), `vcs.defaultBranch`, `--no-check`, `--fail-on-test-failure`, and the earlier `include` → `scope`, `exclude` → `ignore` (D107) hints; they fall back to the generic "did you mean" (edit distance ≤ 2). Wording in C6 §5, §13, §14, recorded points, amendment; C4's C6 recorded point. Rejected: (a) a hint per removed name (the original recommendation); (b) generic hints only (no help for natural mistakes); (c) deprecation warnings (nobody to migrate).
- **CC8 (8/10, ok, option a):** `vcs.ref` / `--vcs-ref` (§12): a non-empty string without whitespace, else a `ConfigError` naming the source; `HEAD`/`CURRENT` matched case-insensitively and normalised to upper case; existence on the host never checked (D205); `/` in branch names kept, URL encoding is C4's when building links. Rejected: (b) full git ref-name rules (re-implements `git check-ref-format`); (c) any string (a stray space or empty value unnoticed until a link is clicked).
- **CC9 (9/10, ok, option a):** C6 checks form only (§5), after the schema, each failure a `ConfigError` naming file and key: `directories` keys literal relative directories, normalised like `scope` entries, rejected when absolute, containing `..` (a `directories` entry configures a directory inside its base; only `paths` may reach upward) or a backslash, glob characters literal (Z10); `kinds` keys `<path>#<name>` split at the last `#`, both non-empty; no leading `!` in `exempt` keys, `paths` or collection members (D188); existence and scope left to C9's warnings. Rejected: (b) no form checks (a malformed key is a typo that can never match); (c) existence checks in C6 (needs the scan and analysis).
- **CC10 (10/10, ok, option a):** `slug` in `directory-config.schema.json`: `^[a-z0-9]+(?:-[a-z0-9]+)*$` (lower-case kebab-case; safe in every URL position and in file names; no case-only collisions; matches CC5); a violation is a `ConfigError`, the pattern shown in the schema `description`. Rejected: (b) RFC 3986 unreserved characters (case question, `a..b`, `~x`); (c) any string, modules encode (breaks C10's "arrives validated").

### Questions (one by one, all ok)

- **QA (1/10, ok, option a; R1#4, R2#21):** a flag only where it has an effect, elsewhere an "unknown flag" error: `--strict`/`--no-strict` on `check`, `build`; `--rule` on `check`, `build`, `dev`; `--no-tests` on `build`, `dev`. Config `tests`/`strict` never an error; ignored by `check`/`init` (`tests`) and `dev`/`init` (`strict`). The user asked why not `dev` (D164: a long-running server can neither refuse to start nor stop mid-edit) and what `--no-tests` does (skips running tests in `build`/`dev`; `check` only lists, never runs). Applied in C6 §6. Rejected: (b) accept everywhere, ignore silently (`dev --strict` would look effective).
- **QB (2/10, ok, option a; R1#5):** the normaliser rewrites a bare `--strict` into the four `--strict=<part>` tokens before `parseArgs` (a following word stays positional, the hint fires), tokens after `--` untouched; flags apply in command-line order: `--no-strict` clears, `--strict`/`--strict=<part>` add (alias overrides work); a repeated `--rule` id: the later value wins. Applied in C6 §3, §14. Rejected: (b) mixing is an error (alias overrides impossible); (c) `--no-strict` always wins (no "only warnings" after a reset).
- **QC (3/10, ok, option a; R1#6, R2#18):** prefix patterns only: no `*` (exact) or one trailing `*` matching anything incl. `/`; a `*` elsewhere a `ConfigError`; the literal prefix is the text before `*`. Keys pinned to a reserved namespace are checked against the CLI's table; any other key is matched against the CLI's table plus the module's declared rules and warned about only when it matches nothing and the module declares `rules` (P14). Applied in C6 §12, §14. Rejected: (b) picomatch globs (fuzzy prefixes, hard tie-breaks); (c) namespace wildcards only (no `represent/missing-*`, no `*`).
- **QD (4/10, ok, option a; R1#8):** a pinned npm name equal to one of the module's static `testRunners` (package name and subpath) resolves like that static (module's location); other pinned references resolve like config references (built-ins; npm from repo root then CLI; `file:` against the config base); with pinning, unpinned candidates are never loaded or detected (no issues from them); a failing pinned runner stays a thrown `PluginError` (CC2). Applied in C6 §11, §14. Rejected: (b) always like config references (a module-offered runner needs a second install); (c) repo root, CLI, then module location (version depends on what's installed where).
- **QE (5/10, ok, option a; R1#7):** without `displayName`, a runner's name (and so its id) is the built-in name, the npm package name plus subpath, a `file:` file's base name without extensions, or a `file:` directory's `package.json` `name`, else its directory name; never a path (C2 §8 rule 2; D186). Applied in C6 §11, §14. Rejected: (b) `displayName` required for `file:` runners; (c) a generic `runner`.
- **QF (6/10, ok, option a; R1#12, R2#14):** C6 §5 gains "Directory-config semantics", the contract C9 implements (where configs live, precedence, node creation, pattern rules, `paths` entry semantics, display keys; `kinds`/`collections`/`exempt` by their decisions), mirrored in schema descriptions and the CLI README; D188's AGENTS note points at it. The `..` form check joins CC9: in `paths`, collection members and `exempt` keys only as a leading run; within-scope stays C9's. Rejected: (b) point D188 at the unplanned C9 (08b stays authoritative meanwhile); (c) keep the details in AGENTS (a log, not a spec).
- **QG (7/10, ok, option a; R2#15):** a collection key is non-empty, not `.`/`..`, without `/`, `\`, `#` or glob characters (`* ? [ ] { } ( ) !`); any other possible file base allowed; a `ConfigError` with the other map-key checks. Applied in C6 §5, §14. Rejected: (b) a strict whitelist (rejects real file bases); (c) no check (confusing downstream failures).
- **QH (8/10, ok, option a; R1#10, R2#22, R2#23):** in `dev`, directory configs reload after a rescan without a restart (`loadDirectoryConfigs` callable again; JS/TS forms with jiti's module cache off); root or package config changes restart (§8.3), and so does a changed set of existing packages (C11 compares after each rescan).
