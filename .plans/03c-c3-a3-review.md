# C3 amendment C3-A3 review (`chunk-03-theme-system.md`, the representation redesign)

> Plan 4 of the redesign's application (08b §12, 08e E7). Status: **draft applied to C3 (2026-10-20); choices K1–K6 settled with the user; two zero-context reviews triaged and every outcome (Q1–Q6, Fix 1–13) settled with the user and applied to C3, C2 (wording) and AGENTS; **plan 4 approved by the user (2026-10-20)**.

## Choices the draft made beyond the decisions (discussed one by one)

- **K1 (ok):** broken links and VCS links without VCS info (both an `<a>` without `href`, D183) get one attribute with two values, `data-link="broken" | "unlinked"` (`tssData.link`), so a theme can flag what the author must fix without flagging what simply can't link; the default theme shows `broken` in `--tss-link-broken` with a dotted underline and `unlinked` as plain text. Rejected: `broken` only (unlinked reachable only through a fragile `a:not([href]):not([data-link])`); two boolean attributes (against the one-attribute-per-state convention, D84). Answers 08b §12's open question for C3.
- **K2 (ok, option a; the association part reversed by Q1):** association levels and node issues get catalogue names **now**, the minimum that mirrors the contract: `tssData.association` (open, like `AssociationLevel`), `tssData.severity` (`error | warning`), the **Issues** area (`tss-issues`, `tss-issue`, `tss-issue-rule`, `tss-issue-location`), `--tss-severity-*` tokens with surfaces, issue component tokens, `--tss-weak-opacity`; `tss-test-file` takes `data-association`. Any module rendering the representation needs them; layout-specific names (coverage, node lists, …) stay C10's additive amendment (01d L9). Rejected: deferring all of it to C10.
- **K3 (ok, option a):** `tssData.status` keeps its eight values, their sources documented: the six `TestStatus` values from runners; `unavailable` for files covered by a runner `error` or a failed root, or when `Tests.status` is `unavailable`; `not-run` from `Tests.status`; the error text goes in `tss-test-error`. Rejected for now: a separate `error` value (the error text already distinguishes it; can be added additively).
- **K4 (ok, option a):** `tss-nav-group` keeps its name, described as a collapsible set of nav links (e.g. a node with children); catalogue names describe UI, not the data model, and "group" is ordinary UI vocabulary. Rejected: `tss-nav-level`/`tss-nav-section` (reads as a depth / clashes with `tss-section`), `tss-nav-node` (ties the catalogue to the data model).
- **K5 (ok, option a):** `-theme-default` under C1 §8: one area `src/themes/` with `DefaultThemes.ts` (class: docs and tests), `defaultThemeFiles.ts` (constant: docs, plus a test that every path exists), one README, tests named after the files; `src/index.ts` re-exports by name (the default export explicitly); `../../css/…` resolution unchanged. The same rules noted for `-lint` and the `-api` `catalogue/` area. Rejected: one area directory per export.
- **K6 (ok):** small naming items as drafted: `data-kind` open (module kinds are further values; unknown kinds fall back to plain `tss-badge`); `data-association` open and `data-severity` closed, mirroring `AssociationLevel` and `Severity` (`off` never reaches the data); tokens `--tss-link-broken` (semantic, interaction group, `failed` pick), `--tss-severity-<s>[-surface]` (semantic, `failed`/warning picks), `--tss-weak-opacity` (component, `--tss-opacity-muted`); issue parts `tss-issue-rule` and `tss-issue-location` only (message and hint plain text; more classes are C10's if needed).

## Agent review (2026-10-20)

Two zero-context reviewers, read-only: **fidelity and fit** (C3 vs 08b, D160–D200, C2 B9/B10, C1 §8, the C3 checklists) and a **theme and module author's read** (can every state of the representation be styled from the catalogue alone; can a module render it). Verdicts: every checklist item covered, no contradiction with the sources and no invented rules beyond K1–K6, D81–D97 unchanged in substance; one real defect found by both (bare `[data-association]` selector), several gaps in where attributes go and what tests need, many precision nits. Triage below; each item discussed with the user one by one; outcomes applied.

### Questions (for the user)

- **Q1 (option c, the user's choice):** association levels get **no catalogue state**: `tssData.association`, `--tss-weak-opacity`, the attribute on `tss-test-file` and the default dimming are dropped (reverses that part of K2). The user: a theme can't predict all the ways a module may want to handle different resource types in different contexts based on associations; that's the module's concern. The finding behind it: a bare `[data-association]` selector broke D92 and the `scoping` lint, and opacity on a showcase would dim the slotted showcase and make a stacking context on a stage ancestor. Rejected: (a) named classes with colour instead of opacity, (b) opacity on named classes only.
- **Q2 (ok, option a):** the Tests area gains `tss-test-runner` (a runner's section), `tss-test-project` (a file result's project label), and `tss-test-error` is documented as the error block at every level (test, suite, file, runner, failed root, unhandled error) with parts `tss-test-error-message`, `tss-test-error-stack`, `tss-test-error-diff`; failed roots and unhandled errors are error blocks inside `tss-test-runner`. Each maps onto a contract field (D186) and has one obvious presentation. Rejected: documenting `tss-test-error` only; deferring to C10.
- **Q3 (option b, the user's choice):** placement fixed only: `aria-expanded` goes on the toggle button that collapses or expands a section (WAI-ARIA disclosure pattern), never on the section; catalogue classes for toggles (and any container state mirror) come with C10's additive amendment. The user: (a), a generic `tss-disclosure`/`tss-disclosure-toggle` pair with `data-expanded`, runs too far ahead into C10's domain. Rejected: (a); (c) leaving the inaccessible placement until C10.
- **Q4 (ok, option a):** `aria-current="location"` kept (H9; acceptable semantics: the place within the page the route points to); one element per shell at a time, removed by the router on route change; the default theme gives it a `--tss-selection` background inside `.tss-content`. Rejected: a `data-target` attribute (changes H9 for a debatable gain).
- **Q5 (ok, option a):** a module renders each doc at most once per page (binding: ids must be unique in the shadow root; a second reference links to the rendered copy); in C3 §1 and as a wording note in C2 §8 rule 6. Rejected: router lookup per container (can't tell copies apart, DOM stays invalid); saying nothing (silent wrong scroll target).
- **Q6 (option a, the user changed their mind after first accepting b):** doc roles get a catalogue state: `tssData.docRole` (`data-doc-role`, values `readme`, `licence`, `changelog`, `other`, open like `DocRef.role`) on `tss-content`, absent for docs without a role; no default style required. Node kinds (`representation`) stay out of the catalogue, stated explicitly in §4 (layout territory; C10 may add one). Rejected: (b) neither.

### Fixes (applied)

- **Fix 1 (ok):** convention: outside `.tss-content` a state is styled only compounded with a catalogue class, never as a bare `[data-…]` selector; every `tssData` entry lists `appliesTo` (in the metadata and the generated "States and variants"): `status` on the six test classes incl. `tss-test-runner`, `kind` on `tss-badge`/`tss-symbol`, `severity` on `tss-issue`, `docRole` on `tss-content`, `link` on doc links and `tss-link`, the rest as before; an unknown `Tests.status` value → no attribute (association dropped by Q1).
- **Fix 2 (ok):** open value sets: unknown values render acceptably with no value-specific rule, themes never assume the list complete; K6's `data-kind` fallback in the plan text; the default theme styles kinds alike (no per-kind tokens).
- **Fix 3 (ok):** prose links styled as `.tss-content a[href]` plus the two `data-link` states; an `<a>` with neither `href` nor `data-link` is an anchor and gets no link styling.
- **Fix 4 (ok):** `data-link` also on `tss-link` outside docs (VCS links in issue locations or nav without VCS info).
- **Fix 5 (ok):** contrast (D85, C12): severity colours on their surfaces and `--tss-link-broken` on `--tss-surface` join the §7 list; C12 recorded (dimmed text dropped with Q1).
- **Fix 6 (ok):** `tss-text-doc` wins over the prose `pre` rule (documented precedence).
- **Fix 7 (ok):** token defaults named consistently ("intended picks; final at implementation", as for alerts).
- **Fix 8 (ok, applied last):** status line and the amendment's "Unchanged" line aligned (§3.4, §7 styles, acceptance 3 and 7; "the default themes' `css/` structure").
- **Fix 9 (ok):** "README" meaning any rendered doc → "doc" (area label "Doc content"; historical records kept).
- **Fix 10 (ok):** §8: the files the generated constants live in; C3's generator replaces C2's hand-written slot, keeping `tss-content`, `tss-theme-switcher` and `cssVar`.
- **Fix 11 (ok):** `-lint`: rule docs live in the package README (no per-rule READMEs); the rule tests test internal files, the exports (constants) need docs only.
- **Fix 12 (ok):** K1 recorded where the contract states it: D183's text and C2 §5.6 (wording, noted in C2's status line).
- **Fix 13 (ok, raised from Q1's finding):** `opacity` (other than `1`) joins §1's layout rule 2 and the `scoping` lint's stage-ancestor list: it dims the slotted showcase and adds a stacking context. An additive restriction in D89's territory, accepted by the user (alternative: record it for C10).
