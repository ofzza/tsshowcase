# Redesign revision 2 review triage (`08b-representation-redesign.md`)

> Four focused clean-context reviews of 08b revision 2 (2026-10-20), run in parallel: **A** = consistency and verdict audit (24 findings), **I** = stage interfaces against principle 1 (24 findings), **W** = walkthroughs over stdblox-react (on disk) and this repo's planned layout (19 findings), **S** = feasibility spikes (Vitest 3.2/4/5 listing, TypeScript 6 API, picomatch, `parseArgs`). Merged below as Z1–Z18 (decisions) and V1–V12 (clarifications and fixes). Status: **resolved** (2026-10-20): group Z decided one by one, group V and the remaining group Y items approved; all folded into 08b revision 3.

## Verdicts

- **A:** every X1–X13 outcome is reflected accurately; gaps are in completeness (decisions missing from §11, effects missing from §12) plus two real design holes (C9 now depends on C7; a configured node never gets its own directory's README).
- **I:** the stage split is sound and most inside-stage rules are genuinely encapsulated, but **principle 1 holds only partly**: half the interfaces are only named, four leaks would force plugin-visible changes later (semantics in `-api` helpers, no module passthrough, ordering left to modules, home-doc defaults left to modules), and two data-shape bugs (test results lose the per-project identity; the runner key is undefined).
- **W:** this repo (dogfooding) passes `check` with almost no configuration, if tests are named after the files they test. stdblox fails with 4 errors from the headless pattern and gives a flat menu with the README duplicated across file nodes until each component directory gets a hand-written collection. Links have real gaps (home docs, roots, files with no role).
- **S:** every assumption holds, with adjustments: Vitest's `globTestSpecifications()` lists files without running them on 3.2, 4 and 5 (fast, reusable instance), but `createVitest` already changes `process.env` and installs handlers, and on 3.x/4.x inline project `root`s resolve against `process.cwd()`; TS 6 handles declaration merging (augmentations and non-instantiated namespaces need rules) and detects components only with `@types/react`; picomatch needs candidate normalisation and escaping; `parseArgs` needs care around a bare `--strict`.

## Outcomes of group Z (discussed one by one)

- **Z1 (2026-10-20):** coverage and per-node test summaries are **module concerns** (presentation): the contract defines neither, no `-api` helper carries their semantics, the CLI computes neither (it needs only run-level test status, for `--strict`). The data already holds what modules need (nodes' `items`, `path`, the tree, `tests` associations, `Representation.tests`). 08b §7.6 leaves the contract; `-base-react` implements its own coverage. The user's correction of Claude's "CLI computes and stores".
- **Z2 (2026-10-20):** the CLI emits every array (children, docs, tests, showcases) in its final default order, stated in the contract; `order` and `ordinal` stay as information; modules may re-sort as a presentation choice.
- **Z3 (2026-10-20):** home doc references carry `role: 'readme' | 'licence' | 'changelog' | 'other'` (open union, assigned by the CLI's existing detection); selection stays the module's; `react-default` shows README and licence by default and offers a `homeDocs` option (patterns or roles).
- **Z4 (2026-10-20):** `AnalysisResult { files: { [path]: { symbols?, showcasingComponents?, meta? } }, issues?, inputs?, state?, meta? }`; `FileSymbol` and `ShowcasingComponent` gain `meta?`, copied verbatim to `RepresentedItem.meta` / `ShowcaseAssociation.meta`; `AnalyzeContext` carries per-package options; package-level issues attach to the package root node, repo-level ones to `Representation.issues` (and the repo home); all printed in the report.
- **Z5 (2026-10-20):** `results: { [file]: TestFileResult[] }` (one per project, `project` kept; updates replace per (file, project)); runners keyed by an opaque CLI-assigned id (display name, de-duplicated with a suffix), the value carrying `name` and, when not a path, `reference`; no machine paths in the data.
- **Z6 (2026-10-20):** one monotonic CLI-assigned `revision` shared by data snapshots and test updates (a module applies a message only if its revision is higher); test-update merge rules: results replace per (file, project), `unhandledErrors`/`failedRoots` replace per runner when present, removed files listed, `tests.status` carried when it changes.
- **Z7 (2026-10-20):** the package root always has id `root:<package dir>` and representation `'root'`; a configured node exactly at the single scope path merges into it (`name`, `slug`, `order`, `paths`), recorded as `configuredBy`; links to that directory resolve to the root.
- **Z8 (2026-10-20, revised after the user reconsidered the check consequence):** a directory `README.md` is **primary** for a configured node at that directory (incl. the root via Z7) and **strong** for every exporting file in that directory, whether or not a configured node exists; the check is satisfied as before (X2); a module may skip a strong doc on a file node when a parent node already shows it as primary. **Association levels renamed:** `primary` (was `exclusive`: name matches, explicit `paths`/collection listings, a configured node's own README) / `strong` / `weak`; documented as primary > strong > weak; the check counts primary and strong.
- **Z9 (2026-10-20, the user's reformulation of link resolution; replaces 08b §7.7's step list):** the CLI only decides **which node** a link targets; the URL stays the module's `resolveRoute`. **Target:** a file link is explicit; a directory link means its `README.md` if it has one (implicit file link), else the directory itself. **Candidates:** for a file, first that file's own nodes (its direct node, its collection's node, configured nodes listing it, ignoring upward references), else the nodes it is associated with (incl. homes for home docs); for a directory without README, its own node (configured node or root) only. **Selection:** strongest association first (primary > strong > weak; a file's own nodes count as primary), then shallowest tree depth, then list order (final CLI order, Z2). **No candidates:** a file → the VCS host (D73); a directory → a link element **without `href`** plus `docs/broken-link` (warning; the target doesn't exist in the representation). **Broken links** (nonexistent, ignored, not represented) all get the same treatment (an `<a>` without `href`, revising D121's unwrapping), with a catalogue state attribute for themes; `docs/broken-link` stays a warning by default. **Fragments:** kept (doc-id-prefixed) when the target is a doc, dropped otherwise. Out-of-scope or outside-package files → the VCS host.
- **Z10 (2026-10-20): deferred** (logged in 08b §13): (a) module-proposed collections (e.g. the `headless` preset) and (b) glob keys in `directories`. Until then, headless components and directory-per-unit layouts are configured explicitly (collections, directory configs) or exempted.
- **Z11 (2026-10-20):** accepted as is: listing a symbol both enables coverage (module) and vouches for it in the check (X6); a broad listing is a deliberate, visible choice with a big effect; documented prominently. A `vouch: false` key can be added later if needed.
- **Z12 (2026-10-20):** super-plan R10: edge C9 → C7 added, C10 → C7 dropped (C11 keeps C7); implementation order C1 → C2 → C4 → C6 → C7 → C8 → C9, then C3 → C5 → C15 → C10 → C11 → …; D29's intent unchanged; planning order unaffected (C7 gains `listTestFiles`).
- **Z13 (2026-10-20):** (a) when **no symbol requires tests** (after kind overrides, module-declared kinds and exemptions; with default kinds: all `constant`/`type`), the test *requirement* is short-circuited: no `tests/no-runner` error and no `--strict` failure for a missing runner (`tests.status = 'not-run'`, reason "no tests required"); runners are still detected, and a detected runner still lists and runs existing tests (e.g. type tests). (b) `check` honours `--strict=warnings` (non-zero exit on warnings); the other parts are ignored by `check`.
- **Z14 (2026-10-20, the user's root-cause fix):** **actions never take optional positional arguments** (required ones, like `init <dir>`, are fine); `build [outDir]` becomes **`build --out <dir>`** (relative to the cwd; config `outDir` relative to the config file; flag > config > `./showcase`; D93's intent kept). `--strict` selects parts only in the `=` form; `build --strict tests` is an unambiguous error ("`build` takes no positional arguments; did you mean `--strict=tests`?"). `--no-strict` is handled by the argv normaliser (overrides config `strict` for the run). Also: empty or unknown part names rejected after parsing; `--rule` split on the last `=`, ids starting with `-` use the `--rule=…` form.
- **Z15 (2026-10-20):** documented only, no warning and no workaround: on Vitest 3.x/4.x, inline projects with relative `root`s resolve against the process cwd (Vitest 5 is unaffected); legacy versions and non-mainline usage. C7's "independent of cwd" test is scoped accordingly.
- **Z16 (2026-10-20):** a `README` in any form (no extension, `.md`, `.txt`) counts everywhere, homes and directories alike; non-markdown renders as plain text. Confirmed by the user ("agreed on both counts"): README matching as for homes (case-insensitive, an exact `README.md` preferred among several); other docs stay markdown (`<base>.md` name matches, explicitly listed markdown); only the `README`/`LICEN[CS]E` names get the plain-text treatment.
- **Z17 (2026-10-20):** listed test files are intersected with the in-scope, non-ignored tree before associations; results for other files are associated with no node and kept only as a run-level count per runner.
- **Z18 (2026-10-20):** the single-file rule is kept as is; the convention "name tests and showcases after the file they cover" is documented; no extra hint in the issue.
